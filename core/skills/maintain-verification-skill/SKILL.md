# Maintain a verification skill

기능 맵은 앱이 바뀌는 순간부터 낡는다. 이 스킬은 `/create-verification-skill`로 생성한 스킬(또는 기능 맵이 있는 프로젝트 로컬 검증 스킬)을 유지하는 루프다. 엄밀함의 단위는 모든 문장이 아니라 기능이다. 모든 기능 파일을 소스로 훑고 모든 기능을 라이브로 실행하되, 모든 불릿을 끝까지 파고들지는 않는다.

## Outcomes

하나를 고르고, 어느 것인지 밝힌다.

- **clean** — 모든 기능이 소스와 라이브 커버리지를 받았고, 내보낼 만한 것이 없다. 브랜치도 PR도 없다.
- **changed** — PR 하나가 증명된 문서, 하니스, 맵 수정을 내보낸다.
- **blocked** — 커버리지를 끝내지 못했거나 증명된 수정을 안전하게 내보내지 못했다. 무엇이 막았는지 정확히 말한다.

## Edit scope

검증 스킬 자신의 디렉터리(SKILL.md, features/, 그 스킬이 소유한 하니스 스크립트)만 수정한다. 실행 중에는 제품 코드를 절대 수정하지 않는다. 맵이 설명하는 동작을 앱이 더는 하지 않는다면, 그것은 문서 드리프트(맵을 고친다)이거나 제품 회귀(보고하고, 문서로 덮어 가리지 않는다)이다.

## Pass

0. **Locate the target.** 유지할 검증 스킬을 찾는다. 본문에 launch/drive 절과 기능 맵이 있는 프로젝트 로컬 스킬이다(보통 `.claude/skills/verify-*/`). 후보가 여럿이면 어느 것인지 묻고, 없으면 대상을 지어내지 말고 멈춘 뒤 `/create-verification-skill`을 안내한다.

1. **Index hygiene.** 기능 맵 README를 읽고 같은 위치의 형제 파일을 glob한다. 빠졌거나, 남거나, 중복되거나, 죽은 항목을 고친다. 가볍게 한다. 생성된 인벤토리는 만들지 않는다.

2. **Source wave.** 기능 파일마다 읽기 전용 서브에이전트 하나를 동시에 띄운다. 각자 "이 사용자 대면 기능은 어떻게 동작하는가?"를 소스에서 설명하고, 인용과 함께 문서 드리프트 가능성을 표시하고, 간결한 라이브 검증 레시피 하나를 반환한다. 자식은 앱을 구동하지 않고 파일도 수정하지 않는다. 반환 형식: feature summary / source entry points / likely drift or none / one recipe.

3. **Reconcile.** 모든 기능 파일에 반환된 요약이 있어야 한다. 겹치는 레시피는 가능한 한 적은 수의 앱 상태로 합친다. 인용된 드리프트는 표본으로 확인하고, 깨끗하다는 주장은 다시 증명하지 않는다. 최근 변경이 잦은 곳을 훑어 맵에 없는 사용자 대면 surface를 찾되, 하나가 빠졌다고 하려면 구체적인 소스 경로를 요구한다.

4. **Live pass.** 소스가 깨끗해 보여도 필수다. 구동은 모두 코디네이터가 맡고, 검증 스킬 자체의 launch 모델을 따른다. 서버와 UI는 오래 사는 인스턴스 하나를 순차로 구동하고, 수명이 짧은 CLI는 구동마다 새로 격리한 세션을 쓴다(어느 쪽인지는 이 스킬이 아니라 그 스킬의 Launch 절이 정한다). 모든 기능을 적어도 한 번 실행하고, 어떤 실패가 나든 패스 내내 세 가지 불변식을 지킨다. (1) 마지막으로 예상 밖 동작을 한 뒤 헬스 체크하지 않은 인스턴스는 구동하지 않는다. 첫 구동 전에 doctor를 돌리고, 세션이 단위인 곳에서는 새 세션마다 doctor를 돌리고, 구동이 실패한 뒤에도 다시 doctor를 돌린다. doctor가 실패를 보지 못하는 경우(정상 프로세스 위에서 UI 상태가 멎은 경우)에는 기대하지 말고 알려진 상태로 리셋하거나 다시 띄운다. (2) 지금까지 수집한 증거는 모든 cleanup을 거쳐 살아남으며, 가정하지 않고 지정된 위치에서 확인한다. (3) 구동이 시작한 것은 그 구동이 쓸모 있는 동안만 산다. 세션이 멎었든, 종료됐든, 공유되든 실패한 반복의 잔여물은 정리한다(공유 인스턴스라면 인스턴스가 아니라 잔여물을 정리한다). 스킬 드리프트로 생긴 doctor 실패는 드리프트다. edit scope 안에서 고치고, 고친 것 때문에 무효가 된 것만 다시 시작해 한 번 재시도한 뒤에야 패스를 `blocked`로 부른다. 닿을 수 없는 기능은 구체적인 선행 조건(인증, 권한, OS, 외부 상태)과 시도한 경로가 있을 때만 `verified-unreachable`이다. 맵이 그 선행 조건을 빠뜨렸다면 그것은 드리프트다. 분류(triage)에서 나온 하니스 수정은 내보내기 전에 라이브로 다시 구동한다. 최종 teardown은 이 재증명을 포함해 실행의 마지막 구동 뒤에 하며, 그래야 실행 뒤에 남는 것이 없다(증거는 스킬이 정한 대로 남는다).

5. **Triage.** 사용자 관점 설명이 틀렸거나 빠졌다면 문서 드리프트이니 고친다. 동작은 정상인데 하니스가 구동하지 못하면 하니스 갭이니 고친다. 하니스 수정은 생성 때와 같은 헬퍼 규칙을 따른다(스크립트는 실행 가능하고, 호출 방법은 스킬 본문에 문서화한다). 앱 동작이 실제로 고장 났다면 제품 갭이니 사용자를 위해 기록하고 이 PR에서는 뺀다.

6. **Ship or stop.** changed라면 증명된 수정을 담은 PR 하나를 만들고, 그 전에 바뀐 파일을 모두 다시 읽는다. clean이나 blocked라면 PR 없이 결과와 커버리지를 솔직하게 보고한다.

간결한 실행 노트(다룬 기능, 닿을 수 없는 선행 조건, 확인된 드리프트, 결과)를 임시 위치에 남기고, 커밋하지 않는다.
